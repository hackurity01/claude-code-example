Section 08

하네스 엔지니어링

하네스의 개념을 이해하고, 지금까지 만든 구성 요소들이 하나의 하네스를 이룬다는 것을 인식한다.

8분 | 하네스, Agent = Model + Harness, 환경 설계

왜 하네스인가 — AI는 확률적이다

Claude에게 같은 요청을 세 번 하면

세 번 다 다른 결과가 나올 수 있다.

AI는 확률적으로 동작하니까.

그런데 오늘 우리가 한 걸 돌아보면...

오늘 우리가 한 일의 의미

CLAUDE.md로 "이렇게 해라"를 알려줬더니

→ 코드 스타일이 일관됐다

Hooks로 "이건 차단해라"를 강제했더니

→ .env 수정이 불가능해졌다

Skill로 "이 순서대로 해라"를 정했더니

→ 리뷰가 매번 같은 형식으로 나왔다

에이전트로 "이 사람이 한다"를 정했더니

→ 역할별로 전문화된 결과가 나왔다

오케스트레이션 스킬로 "이 팀이 이 순서로"를 설계했더니

→ 한 번의 명령으로 리뷰+테스트+문서가 완성됐다

이 모든 것이 하나로 합쳐진 게 바로 하네스입니다.

하네스의 정의

하네스(Harness) = 모델 바깥에서 모델의 행동을 잡아주는 모든 장치 Agent = Model + Harness — Mitchell Hashimoto (HashiCorp/Terraform 창시자)

궁극적 목표

작업의 모호함과 불확실성을 구조적으로 제한하여,
확률적 시스템에서 일관된 결과를 만드는 것.

"모델의 문제가 아니라 환경의 문제다." — HumanLayer

오늘 만든 것이 이미 하네스다

구성요소역할상태
CLAUDE.md"이렇게 해라" (가이드 — 무시될 수 있음)완료
Hooks"매번 자동으로 해라" (자동화 — 반드시 실행됨)완료
Skill"이 순서대로 해라" (절차)완료
Agent 정의"이 사람이 한다" (역할 분담)완료
오케스트레이션 스킬"이 팀이 이 순서로" (협업 설계)완료

→ 이 5가지가 합쳐진 것이 하네스

하네스는 열린 개념

하네스 엔지니어링

= 확립된 방법론이 아니라

= "모델의 환경을 설계해서 일관된 결과를 만든다"는 접근법

Claude가 실수하면,

프롬프트를 고치기 전에

하네스에 뭘 추가할 수 있는지 먼저 생각해보자.
