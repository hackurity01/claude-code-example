CLAUDE.md, Rules

CLAUDE.md를 작성하고 Settings 계층을 이해하여, Claude Code의 출력 품질을 구조적으로 제어할 수 있다.

20분 | CLAUDE.md, Settings, /init, /permissions

CLAUDE.md란 -- "프로젝트의 기억"

  • CLAUDE.md = Claude를 위한 온보딩 문서
  • 매번 반복하지 않아도 Claude가 항상 참고
  • Git에 커밋 → 팀 전체가 같은 규칙 공유
새 팀원이 합류하면? → 온보딩 문서를 준다 Claude가 합류하면? → CLAUDE.md를 준다

Boris (Claude Code 창시자):

"We check it into git. The whole team contributes multiple times a week."

"Claude가 실수할 때마다 CLAUDE.md에 추가하세요."

왜 필요한가 -- Before/After

CLAUDE.md 없이 유틸 함수를 추가하면?

→ 함수만 만들고 끝. 테스트 없음. → 팀원마다 코드 스타일이 제각각. → "테스트 작성해줘"를 매번 말해야 함.

CLAUDE.md 하나 추가하면?

→ "새 기능엔 테스트 포함" 규칙 → 자동으로 테스트 작성 → 팀 전체가 동일한 규칙 → 매번 말할 필요 없이 규칙 적용

Claude는 명시적으로 요청하지 않으면 테스트를 안 쓰는 경우가 많다. CLAUDE.md에 규칙이 있으면 → 요청 없이도 팀 규칙대로 동작.

계층 구조 -- 4단계

CLAUDE.md 계층 구조 (위에서 아래로 적용) ┌─────────────────────────────────────────────────┐ │ 1. ~/.claude/CLAUDE.md 개인 전역 설정 │ │ "항상 한국어로 응답해줘" │ │ (모든 프로젝트에 적용, 나만 사용) │ ├─────────────────────────────────────────────────┤ │ 2. ./CLAUDE.md 팀 프로젝트 규칙 │ │ "TypeScript strict mode" │ │ (git에 커밋 → 팀원과 공유) │ ├─────────────────────────────────────────────────┤ │ 3. ./CLAUDE.local.md 개인 로컬 설정 │ │ "내 환경에서는 포트 3001 사용" │ │ (.gitignore에 추가, 나만 사용) │ ├─────────────────────────────────────────────────┤ │ 4. ./packages/foo/CLAUDE.md 하위 디렉토리 규칙 │ │ "이 패키지는 React 18 사용" │ │ (모노레포에서 패키지별 규칙) │ └─────────────────────────────────────────────────┘

/init으로 자동 생성

Claude Code 대화 중 /init
  • Claude가 프로젝트를 분석해서 CLAUDE.md 초안 생성
  • package.json, tsconfig, eslint 설정 등을 읽고 프로젝트에 맞는 규칙 제안
  • 초안을 기반으로 팀 규칙을 추가/수정

생성 후 확인할 것:

  • 프로젝트 설명이 맞는지
  • 불필요한 내용은 없는지
  • 팀에서 반드시 지켜야 할 규칙이 빠지지 않았는지

## 좋은 예시 ## 핵심 규칙 - TypeScript strict mode 필수. any 금지 - 컴포넌트는 함수형만 사용 - 유틸 함수에 단위 테스트 필수 (Vitest) - 커밋: Conventional Commits

판단 기준: "이 규칙이 없으면 Claude가 실수하나?" → 아니오면 삭제

참고 -- Andrej Karpathy의 CLAUDE.md

출처: github.com/forrestchang/andrej-karpathy-skills

원칙핵심
1. Think Before Coding가정을 명시하라. 불확실하면 물어봐라. 여러 해석이 있으면 제시하라.
2. Simplicity First요청된 것만 구현. 추측성 추상화/설정/에러처리 금지. 200줄이 50줄로 가능하면 다시 써라.
3. Surgical Changes요청한 것만 수정. 주변 코드 "개선" 금지. 기존 스타일에 맞춰라.
4. Goal-Driven Execution성공 기준을 정의하고 검증까지 루프. "버그 수정" → "재현 테스트 작성 후 통과시켜라".

Settings 3단계 -- 설정의 계층

permissions 도구/명령 허용·차단  |  allowedTools MCP 도구 허용  |  env 환경 변수  |  model 기본 모델  |  plugins 플러그인 목록

Settings 계층 구조 (위가 우선) ┌─────────────────────────────────────────────┐ │ CLI Args (최우선) │ │ 세션별 임시 설정 │ │ claude --model opus │ ├─────────────────────────────────────────────┤ │ Project (.claude/settings.json) │ │ 팀 공유 (git 커밋) │ │ Local (.claude/settings.local.json) │ │ 내 로컬만 (.gitignore) │ ├─────────────────────────────────────────────┤ │ User (~/.claude/settings.json) │ │ 내 전역 설정 (최하위) │ └─────────────────────────────────────────────┘
  • 팀 규칙 → Project 레벨 (git 커밋하여 팀 공유)
  • 내 환경만 → Local (git에 안 올라감)
  • 개인 전역 → User (팀 규칙과 충돌 시 팀 규칙 우선)

/permissions -- 권한 빠른 설정

Claude Code 대화 중 /permissions
  • 자주 쓰는 명령을 허용 목록에 추가
  • "이 명령을 실행해도 될까요?" 반복 질문 제거
  • 예시: npm test, npm run build, npx vitest 허용

팁: 처음에는 normal 모드로 시작. 어떤 도구가 쓰이는지 파악한 후 → 자주 쓰는 것만 허용

--dangerously-skip-permissions

bash claude --dangerously-skip-permissions

언제 쓰나

  • CI/CD 파이프라인에서 자동화할 때
  • 신뢰할 수 있는 환경에서 반복 작업

언제 쓰면 안 되나

  • 일반 개발 환경 (중요 파일 삭제 가능)
  • 처음 써보는 프로젝트

모든 권한 확인을 건너뛰고 Claude가 자유롭게 실행. 파일 수정, 명령 실행, 삭제까지 확인 없이 자동 진행.

정리 -- CLAUDE.md + Settings 한눈에

┌─────────────────────────────────────────────────────┐ │ CLAUDE.md │ │ "Claude야, 이렇게 일해" (가이드라인) │ │ - 코드 스타일, 커밋 규칙, 테스트 정책 │ │ - Claude가 참고하지만 무시할 수도 있음 │ ├─────────────────────────────────────────────────────┤ │ Settings │ │ "이건 할 수 있고, 저건 못 해" (권한) │ │ - 도구 허용/차단, MCP 서버, 모델 설정 │ │ - 구조적으로 강제됨 │ └─────────────────────────────────────────────────────┘
  • CLAUDE.md = 무엇을 할 것인지 (가이드라인)
  • Settings = 무엇을 할 수 있는지 (권한)
  • 둘 다 git에 커밋하면 팀 전체에 일관성

실습 Part 2 -- CLAUDE.md 작성

4분 /init으로 시작 → 팀 규칙 추가

CLAUDE.md # TaskFlow 프로젝트 규칙 ## 프로젝트 개요 팀 업무 관리 웹 앱. Next.js 15 + TypeScript + Prisma + SQLite. ## 코딩 규칙 - TypeScript strict mode 사용. any 타입 금지 - 컴포넌트는 함수형만 사용 (class 컴포넌트 금지) - API 응답은 반드시 타입을 정의하고 검증 - 새 기능 추가 시 반드시 테스트 코드 포함 - console.log는 프로덕션 코드에 남기지 않음 ## 커밋 규칙 - Conventional Commits: feat:, fix:, refactor:, test:, docs: - 커밋 메시지는 한국어로 작성 ## 테스트 - Vitest 사용 - 테스트 파일은 __tests__/ 디렉토리에 소스 구조를 미러링
